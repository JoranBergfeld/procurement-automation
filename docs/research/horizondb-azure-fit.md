# Research: Azure HorizonDB beside Azure SQL Database (General Purpose vs Business Critical)

- **Question:** "Is this also the case for HorizonDB? Would that be a suitable candidate as well?" What does "HorizonDB" refer to, and how does it compare with Azure SQL Database General Purpose (GP) and Business Critical (BC) for the procurement-agent plan? The plan: Sweden Central primary, West Europe warm standby, customer-initiated failover, provisional RTO 4 hours and RPO 15 minutes for committed procurement records and evidence, an EU/EFTA data boundary, and Azure SQL Database with SQL Ledger plus separate Blob evidence and digest storage.
- **Binding constraints from closed issues (compared in section 4):** an accepted event, its SQL Ledger entry and the mutable workflow/projection update commit atomically; evidence-required events are accepted only after immutable evidence is durably stored and its protected reference plus content hash is committed; stable source/event IDs give idempotent retries and identical receipts; SQL Ledger is authoritative for accepted events and corrections.
- **Access date for every source:** 2026-11-26. Public Microsoft first-party pages, the Microsoft Online Services SLA document, and one upstream PostgreSQL page. Page text was read for every cited page unless listed under "Access failures" (section 9). Citations are bracketed IDs such as [H7], defined in section 8.
- **Out of scope:** any decision to change databases, prices, performance, and any inspection of an environment, tenant or subscription (none was done; nothing was deployed or measured). "This" in the question points at an earlier statement the author of this note could not see, so the Azure SQL GP/BC facts are stated neutrally in section 3.
- **Search hygiene:** searches used only public product and documentation terms. No project content was sent to search engines or third parties.

## 1. Verdict (conditional)

**On published evidence Azure HorizonDB is not a like-for-like substitute for Azure SQL Database with SQL Ledger in this plan. It becomes a candidate only if a separately evidenced tamper-evidence design is built and a regional-recovery design that fits the objectives is proven. No equivalence is claimed from the database category alone ("transactional database").**

1. **Identification.** "HorizonDB" matches exactly one product in Microsoft's public sources: **Azure HorizonDB**, a fully managed, PostgreSQL-based database service. It reached general availability in the November 2026 release (preview from June 2026). It is not Azure Cosmos DB, Azure SQL Hyperscale or Azure Database for PostgreSQL flexible server (section 2). Residual uncertainty: this is name-matching against public sources, so which product the requester intended cannot be confirmed from here.
2. **Availability SLA: none found.** The 17 November 2026 consolidated Microsoft Online Services SLA (the newest edition listed; the 1 November 2026 edition was also checked) has no HorizonDB entry, and no HorizonDB documentation page states an availability percentage or service-credit terms. A Microsoft Well-Architected page tells readers to confirm the SLA in that document, so this may be publication lag. Do not assume a number, and do not transfer the SQL Database or PostgreSQL flexible server SLA to it (section 3).
3. **Regional recovery does not match the plan.** Microsoft states that "Azure HorizonDB clusters run in a single Azure region" and that the cluster is unavailable if the region is. There is no cross-region replica, warm standby or failover. Regional recovery is a geo-restore of geo-redundant backups into a new cluster: documented RPO up to 1 hour, RTO "a few minutes to a few hours", no numeric RTO commitment. The provisional targets are RPO 15 minutes and RTO 4 hours (sections 3 and 4).
4. **Region mismatch.** West Europe is not a listed HorizonDB region. Europe lists only Germany West Central and Sweden Central. Sweden Central's Azure pair is Sweden South (restricted-access region), also not listed. Microsoft's pages disagree on whether geo-restore can target only the paired region or any HorizonDB region.
5. **No built-in tamper-evidence.** No ledger, immutable-table or tamper-evidence capability appears in the HorizonDB documentation. The extension list has `pgaudit` (activity auditing) and `pgcrypto` (cryptographic functions). "SQL Ledger is authoritative for accepted events and corrections" cannot be met natively. It would need a custom, independently verified design (sections 4 and 5).
6. **What does fit.** PostgreSQL transactions (an event row, an application-managed chain row and a projection update can share one transaction; this is upstream PostgreSQL behaviour and needs a test). Committed transactions survive in-region failover. Private Link. Customer-initiated planned failover within the region. Idempotent keys through unique constraints and `INSERT ... ON CONFLICT` (upstream).
7. **GP vs BC.** HorizonDB documentation describes compute SKUs and reader-node high availability, not GP/BC service tiers. The Azure SQL Database distinctions that can be verified (identical availability credit thresholds for GP and BC; RPO/RTO SLA only for BC active geo-replication) have no published HorizonDB counterpart. "This" therefore cannot be confirmed for HorizonDB for any SLA-based property.

## 4. Mapping to the binding architecture requirements

Classification: **Documented** = stated on a HorizonDB page. **Upstream** = documented for PostgreSQL itself [P1], not confirmed for HorizonDB, so test it. **Custom** = would be our own design. **Gap** = not available. **Unknown** = not verifiable from public pages.

| Requirement | What the sources show | Status |
|---|---|---|
| Accepted event, its ledger entry and the mutable workflow/projection update commit atomically | HorizonDB claims "full ACID guarantees" and acknowledges a commit only after its WAL is durable across zones [H1], [H7]. Multi-statement transactions are ordinary PostgreSQL behaviour; isolation and locking details are not documented on the pages read. No HorizonDB ledger capability was found (section 3), so the "ledger entry" would be an application-managed table (for example a hash chain) written in the same transaction. A single chain head is a serialisation point under concurrent writers (inference). In SQL Database the engine produces the ledger rows for the transaction [Q4]; one transaction can update up to 200 ledger tables [Q6] | Atomicity achievable in principle (Documented + Upstream). The ledger half is **Custom**. Equivalence to SQL Ledger not shown |
| Evidence-required events accepted only after immutable evidence is stored and its protected reference plus content hash is committed | An ordering rule in the application and the Blob store, not a database feature: store the evidence in immutable Blob storage, then commit the reference and hash. The same under either database. The `azure_storage` extension exists [H13]; its fit for evidence was not assessed. The difference is the committed reference/hash row: under SQL Ledger it is itself tamper-evident [Q4]; under HorizonDB it is an ordinary row unless the design in the next row covers it | Same application-level ordering. Tamper-evidence of the row depends on the next row (**Custom**) |
| Stable source/event IDs give idempotent retries and identical receipts | Unique constraints and `INSERT ... ON CONFLICT DO NOTHING` / `DO UPDATE` are PostgreSQL features, and `DO UPDATE` is described as guaranteeing "an atomic INSERT or UPDATE outcome ... even under high concurrency" [P1]. HorizonDB tells clients to retry the whole transaction after failover [H7], which suits idempotent keys. Receipts must be rebuilt from persisted rows. A receipt that cites a ledger transaction or digest has no HorizonDB source | Feasible (**Upstream**). Ledger-linked receipts are **Custom** |
| SQL Ledger is authoritative for accepted events and corrections | Built in for SQL Database [Q4], [Q5]. Nothing equivalent found for HorizonDB (section 3). A substitute would have to show the evidence listed in section 5. Microsoft's own guidance: digests must live in storage that high-privileged users can't alter, and Ledger detects but cannot prevent tampering by someone controlling the machine [Q4], [Q5]. A custom chain inherits the same limits. DR interplay (inference): SQL Database issues automatic digests only for data already replicated to geo-secondaries [Q5], so a digest never refers to data a geo-failover could lose. A scheduled anchor on a custom chain has no such coupling, and a geo-restore up to an hour behind could predate the latest anchored digest | **Gap**, closable only by a **Custom** design with evidence |
| Private connectivity | Private Link is supported; public access stays on until explicitly disabled; no virtual network injection [H1], [H9]. SQL Database has the equivalent setting [Q3] | Met with explicit configuration (Documented). New endpoints and DNS after geo-restore |
| Controlled, customer-initiated failover to a warm standby in a second region | Planned failover is in-region only. Regional recovery is a restore into a new cluster; "Backups don't provide running compute capacity or an additional database endpoint" [H2], [H3], [H7] | **Gap** |
| Provisional RPO 15 min and RTO 4 h | Regional RPO up to 1 hour is documented [H4]. RTO has no numeric commitment and Microsoft says to measure it [H4], [H7]. In-region failover loses no committed transactions [H2], [H7] | RPO not met by documented behaviour. RTO **Unknown** until tested |
| Sweden Central primary, West Europe warm standby | West Europe is not a HorizonDB region [H1]. No warm-standby concept [H7]. Sweden Central pairs with Sweden South, which is a restricted-access region [A1] and not a listed HorizonDB region [H1]. "Currently enabled in selected regions" leaves geo-redundant backup in Sweden Central unconfirmed [H5] | **Gap** as specified. Geo-redundant backup availability in Sweden Central: **Unknown** |
| EU/EFTA data boundary | General rule for regional services [A2]. Sweden Central and Germany West Central, the only European HorizonDB regions [H1], are in EU member states. No HorizonDB-specific statement found | Region-level fit plausible; **Unknown** until Microsoft states HorizonDB coverage |

## 5. Evidence a HorizonDB substitute would have to show

These are design obligations, not product features. None is provided or documented by HorizonDB.

1. **Atomicity.** A test that the accepted-event row, the chain/ledger row and the projection update commit or roll back together under concurrent writers and under failover, and that a retry with the same event ID returns an identical receipt.
2. **Append-only enforcement.** Roles without UPDATE, DELETE or TRUNCATE on event and correction tables, and a record of who holds privileged roles. `pgaudit` is listed as providing auditing functionality [H13]; nothing found says it makes stored rows tamper-evident (inference: it records activity).
3. **Tamper-evidence.** Chain-head digests anchored outside the database on a defined cadence, in immutable storage (Microsoft names immutable Blob storage and Azure Confidential Ledger for SQL Ledger digests [Q4]; using them for a custom chain is an inference, not a HorizonDB integration). An independent verifier that recomputes the chain, and a demonstrated detection when a privileged user alters a row.
4. **Recovery.** A written procedure for a restore that is older than the latest anchored digest: who may declare events lost, how digests are reconciled, how identical receipts are re-issued.
5. **Evidence linkage.** Immutable evidence blobs (as in the current plan) with the reference and hash row covered by item 3.
6. **Residency.** Confirmation of the boundary for the database, the paired-region backup copy and the anchors.

## 6. What would change this verdict

- Microsoft publishes a HorizonDB SLA with credit terms (check the next consolidated SLA revision, or ask the Microsoft account team).
- Microsoft documents a cross-region replica or standby, or a regional recovery with an RPO at or under 15 minutes and a measured RTO.
- HorizonDB gains a native ledger or immutability capability, or a supported extension that provides one.
- HorizonDB becomes available in West Europe, or the plan's secondary region changes to a supported one. Microsoft confirms geo-redundant backup in Sweden Central and the geo-restore destination rules.
- Microsoft states HorizonDB's EU Data Boundary coverage.

## 7. Limits of this evidence

- "None found" for an SLA is an absence in the two November 2026 editions of the consolidated SLA (1 and 17 November) and in the HorizonDB pages on 2026-11-26. HorizonDB went generally available in the same month and a Well-Architected page points to the SLA document, so an entry could appear later. It is not evidence that no SLA will exist.
- Microsoft's pages conflict on two points: the geo-restore destination (paired region only [H1], [H5], [H6], [H8] versus any HorizonDB region [H7]) and what drives restore time (database size [H4] versus WAL replay, "not on database size" [H8]). Public pages can't resolve either. A controlled restore test could.
- Behaviour tagged **Upstream** is documented for PostgreSQL [P1], not for HorizonDB. The HorizonDB-side claim is the general "full ACID guarantees" statement [H1].
- The SQL Database side relies on the SLA document and the Learn pages in section 8. SQL Database availability in Sweden Central and West Europe, and its service-level EU Data Boundary status, were not re-verified.
- HorizonDB pages read are dated 2026-10-27 to 2026-11-24 (release notes 2026-06-02), shortly after general availability, and say that features and regions are "subject to change".
- Whether Sweden Central is among the "selected regions" for geo-redundant backup, and whether a geo-restore into the restricted Sweden South region is possible, are unknown. Checking would need a look at a tenant, which was out of scope.
- Nothing was deployed or measured: no RPO, RTO or failover timings exist.
- The statement that "this" in the question refers to was not visible to the note's author.
