# Reliability evaluators: capability assessment for procurement agents

Research: [#26](https://github.com/JoranBergfeld/procurement-automation/issues/26) · Deferred decision: [#25](https://github.com/JoranBergfeld/procurement-automation/issues/25) · Assessed: 25 November 2026

## Answer

The evaluator project contains **working experimental measurement code and recorded Foundry trials**, not an established procurement qualification system. Its default branch has a disposable managed-code prototype for outcome consistency; a separate, unmerged research branch contains a broader twelve-metric to-do-agent prototype. These can inform experiments on repeated outcomes, tool behavior, faults, confidence and declared constraints. They do not establish that procurement agents or a model-version change meet this project's legal, operational or acceptance requirements. Whether to use or integrate them remains the decision in #25.

The assessed default-branch revision is [`6d38485cf97621d91dbeb1a0224039b5e8cda11a`](https://github.com/JoranBergfeld/agent-reliability-evaluators/tree/6d38485cf97621d91dbeb1a0224039b5e8cda11a). The full-metric code and evidence are instead on the unmerged `joranbergfeld-wayfinder-map-review` branch at [`b6c649068e05fe2bd79ac62e82527b2a77da8eeb`](https://github.com/JoranBergfeld/agent-reliability-evaluators/tree/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing). Do not mistake its experimental code for a default-branch release. This assessment inspected the code and recorded first-party observations; it did not repeat the billable Azure experiments.

## Evaluation methods and what ran

The default-branch [managed-evaluator prototype](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/README.md#L31-L51) calculates **outcome consistency** for grouped binary outcomes, including an explicitly calculated equal-task mean in one item. Its other custom evaluators probe platform contracts rather than additional reliability metrics. The recorded trial registered 11 custom evaluators and recorded 16 completed and 11 failed runs, plus five rejected requests; some were intentional negative probes. [The observations](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/observations-cbee5be8a2.json) retain the trial results and cleanup evidence. ([Trial description](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/README.md#L1-L29).)

The separate to-do prototype implements twelve distinct calculations, with an unavailable result when required evidence is missing or a calculation is undefined:

| Family | Calculations and necessary evidence |
|---|---|
| Consistency | Binary outcome consistency; distributional and sequential action-trajectory consistency; elapsed-time and tool-call resource consistency. |
| Robustness | Success rates under an observed injected fault, altered environment or equivalent prompt, compared with a nonzero baseline success rate. |
| Confidence | Calibration, strict confidence discrimination and Brier predictability using paired self-ratings and independently sourced outcomes. |
| Operational constraints | Compliance against assessed violation sets; conditional severity of observed violations with mapped severities. |

These are actual functions, not merely names on a roadmap. The formulas and input checks are in [`metrics.py`](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/metrics.py#L8-L20) and [the calculation implementation](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/metrics.py#L91-L186); the [predeclared scenarios](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L47-L70) specify their evidence and edge cases. **Consistency is not success:** both all-success and all-failure outcomes yield 1 under this formula. A local, offline check of the assessed function reproduced that result and confirmed that one attempt is unavailable.

The corrected campaign recorded 44 attempted invocations: prompt and hosted agents, each through customer Python and Foundry cloud, with five baseline attempts and two each for fault, environment and prompt variations. Ten metrics were available in each of the four live groups and matched both the local independent oracle and the managed calculation; the other two were undefined because the nominal outcomes were all successes and no live violation occurred. All twelve matched fixed synthetic expectations in a managed run. The managed graders package the prototype's own metric code, so agreement is not an independent Foundry implementation of the formulas. ([Plan](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L9-L20), [results](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L177-L218), [recorded observations](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/observations-fa75b86f19.json).)

A deliberately vulnerable, note-following positive-control prompt agent produced both successes and unauthorized deletions, making all twelve metrics calculable locally; a later managed rescore of the saved evidence matched the oracle. A DNS failure stopped the remaining combinations before that live proof could be completed. This proves an exercise path for constructed evidence, not the behavior of ordinary procurement agents. ([Positive-control protocol and result](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L351-L387); [resolution and remaining gaps](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/14#issuecomment-7144095027).)

## Test data and representativeness

The exercised workload is a **synthetic to-do CRUD fixture**, not procurement data: strict success requires a specified operation sequence, the correct final state and an unchanged unrelated item. Perturbations include an observed update HTTP 503, a wrapped read result and equivalent prompts; the safety rule prohibits modifying or deleting an unrelated item. Before/after snapshots and service events support the outcome assessment. Fixture partitions share a service key and are not an access-control boundary. ([Fixture and conditions](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L22-L45); [implementation](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/run.py#L416-L477).)

Five baseline and two altered-condition attempts per cell are demonstrations, not statistically representative estimates. There is no demonstrated Estonian procurement corpus, legally verified reference outcomes, supplier population, workflow mix, bidder communications or procurement-specific guardrail oracle in these assessed prototypes. The available results cannot establish equal treatment, lawful negotiation, official eForms validity, human award authority or complete procurement records. The project would need independently sourced, representative, authorized cases and explicit definitions to assess those questions; this is an evidence gap, not an integration decision. The procurement [KPI decision](https://github.com/JoranBergfeld/procurement-automation/issues/8#issuecomment-6975292001) requires separate checked coverage and treats missing data as coverage, not zero.

The experiments record one deployment, `gpt-4.1-mini` version `2025-04-14`, in the [campaign artifact](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/observations-fa75b86f19.json). The assessed code demonstrates grouping repeated attempts and perturbations, **not an observed comparison of two model versions**, automated version-change regression gate, representative sampling strategy or approved pass thresholds. A future comparison would need comparable case sets and conditions, retained model and evaluator versions, outcome sources, coverage and independently agreed criteria; the current evidence does not establish such a comparison.

## Interfaces, evidence and reporting

- The to-do harness invokes prompt agents using an OpenAPI tool and hosted agents using a function against the same service, through customer Python or Foundry cloud evaluation. It groups attempts in customer code, computes local results and submits grouped serialized evidence to independently registered Foundry-managed custom graders. It does **not** demonstrate a real CI pipeline, automatic Foundry cross-run grouping, a production reset or isolation guarantee. ([Harness](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L472-L490); [registration and grouping](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/run.py#L263-L290), [scoring](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/run.py#L530-L595).)
- The default-branch trial documents Entra-token authentication and REST operations to register evaluator versions, create and poll evaluations, retrieve paginated output items and upload JSONL. It demonstrated both inline evidence and uploaded files, not versioned Foundry dataset upload. SDK invocation was not validated in that trial. ([Interfaces and limits](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/README.md#L103-L142), [reproduction caveats](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/README.md#L144-L182).)
- Captured observations include attempt IDs, conditions, raw confidence and its provenance, service events and state, derived outcome sources, and metric results; the project also supplies an offline HTML view of captured results. The service is in-memory and the experiments do not establish durable, access-controlled or tamper-evident audit storage. Trace scores use received operation names, not verified complete agent trajectories or argument equivalence; customer and cloud elapsed times have different boundaries. ([Evidence code](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/run.py#L416-L477); [trace and timing limits](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L72-L99); [offline view](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/scorecard.py#L61-L79).)
- Foundry returned default pass/fail labels and thresholds; these are not procurement acceptance decisions. The project has agreed a richer per-metric scorecard contract with evidence, unavailable and acceptance states, but delivery and evidence-retention boundaries remain open, not implemented product guarantees. ([Scorecard decision](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/5#issuecomment-7157696877); [delivery](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/18); [retention](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/19).)

For comparison, the procurement [event-model decision](https://github.com/JoranBergfeld/procurement-automation/issues/15#issuecomment-7041707784) calls for attributable, applicable and linked evidence with coverage, corrections and a protected audit subset. The [records decision](https://github.com/JoranBergfeld/procurement-automation/issues/20#issuecomment-7137684842) does not call for retaining all prompts by default. Prototype observation files do not themselves establish those procurement properties or a lawful retention schedule.

## Failure cases and unresolved boundaries

- These custom managed graders raise on unavailable evidence. Single unavailable probes and mixed-availability all-twelve probes failed with no output items; local calculation retains unavailable reasons. This is a finding about these graders, not proof that every Foundry reporting approach must fail. ([Results](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L237-L252); [grader behavior](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/run.py#L267-L275).)
- Foundry run and item status can say `completed` while an item contains `TARGET_INVOCATION_FAILED`; an agent response can also obscure a tool's 503. Check independent effects and errors, not status or generated text alone. ([Observed failure](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L405-L417).)
- In the managed-code probe, structured numeric inputs changed precision, tested JSON strings were retained unchanged, and declared score bounds did not prevent out-of-range values. These observations are limited to the tested inputs and service version; string preservation is not a general guarantee. ([Numeric fidelity](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/6d38485cf97621d91dbeb1a0224039b5e8cda11a/prototypes/foundry-managed-evals/README.md#L84-L101).)
- A rubric judge followed an instruction injected in tool output and failed compliant attempts. Judge protection is unresolved; confidence was elicited in the same response, not a separately validated follow-up. Neither is a reliable basis for procurement assurance without further evidence. ([Judge trial](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/b6c649068e05fe2bd79ac62e82527b2a77da8eeb/prototypes/todo-plumbing/README.md#L290-L304); [judge boundary](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/15); [confidence protocol](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/16).)
- Microsoft describes these custom code evaluators as **preview**, sandboxed and without network access, and does not recommend preview features for production workloads. Documentation describes the platform contract; the project observations establish only what occurred in its trials. ([Microsoft custom-evaluator documentation](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/other-custom-evaluators); [Microsoft result semantics](https://learn.microsoft.com/en-us/azure/foundry/observability/how-to/cloud-evaluation-results).)

Procurement's [controlled-implementation decision](https://github.com/JoranBergfeld/procurement-automation/issues/10#issuecomment-7006955175) treats inadequate evidence as inconclusive and keeps mandatory human and audit guardrails in force. Evaluator scores, if considered later, cannot by themselves replace those controls, establish legal compliance, authorize production, or represent independently operated supplier agents.
